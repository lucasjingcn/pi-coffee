# MCP 2026-07-28: current support and upgrade path

Status: **not implemented by the pinned SDK; tracked, not guessed.**

## What we run today
- `@modelcontextprotocol/sdk` is pinned in `package.json` (1.32.x). Its server surface implements the
  stateless request/response behaviour we rely on, but it does **not** export a `server/discover`
  method or the 2026-07-28 stateless-transport contract.
- `src/index.ts` builds a fresh `McpServer` per HTTP request and creates
  `StreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })`, so the
  daemon is already stateless at the transport layer; there is no session stickiness to remove.
- `src/mcp-server.ts` exports `MCP_TOOL_ORDER`; `buildServer` asserts the actual registration order
  against it, so tools cannot be added or reordered silently. `tests/docs-consistency.test.mjs`
  enforces tool order, annotations, README tool rows and config names.
- `/internal/capabilities` advertises the daemon version, feature list, MCP tool order and internal
  endpoints for operators and the worker extension.

## Upgrade path (when the SDK ships the contract)
1. Bump `@modelcontextprotocol/sdk` to the first release exporting the 2026-07-28 server APIs
   (stateless discovery/`server/discover`, capability negotiation). Record the version gate in
   `docs/plans/p0-p1-development.md` §P1-5.
2. Keep building the server per request; replace the transport constructor and emit the capability
   document from `/internal/capabilities` so both surfaces agree.
3. Add a protocol-contract test that asserts the negotiated version/capabilities and that every
   `MCP_TOOL_ORDER` tool keeps its annotations; treat unknown protocol versions as fail-closed.
4. Do not invent a handshake ahead of the SDK: clients would see a version they cannot negotiate.

## Non-goals
- No dual-protocol shim and no hand-maintained JSON schema of the MCP transport.
- No change to tool semantics in the protocol upgrade; only the transport/capability layer moves.
